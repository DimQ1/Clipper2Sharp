# План ускорения Clipper2Sharp (раунд 3)

Документ фиксирует, где порт стоит сейчас, какие выводы предыдущих раундов
подтверждены новыми измерениями, и что делать дальше: по фазам, с ожидаемым
эффектом, риском для битовой точности и способом проверки.

Точка отсчёта: `Results/BASELINE.md` (25.09.2026), `docs/porting-notes.md` §4.
Все новые измерения этого раунда сделаны на той же машине (12 логических
ядер, .NET 10.0.12, фоновая нагрузка 75–85% CPU).

## Проверка 07.10.2026: .NET 11 и следующие резервы

Сравнение одной Release-сборки `Clipper2.PortProfile` (`net10.0`) на runtime
10.0.12 и 11.0.0-preview.4.26230.115. Три последовательных раунда, порядок
runtime менялся в каждом раунде; четыре нагрузки, минимум 10 повторов и
1.5 секунды измерения после 700 мс прогрева. Ниже минимум из трёх `best`:

| нагрузка | .NET 10, мс | .NET 11 Preview 4, мс |
|---|---:|---:|
| union | 156.144 | 156.660 |
| offset27 (Miter) | 3.350 | 3.361 |
| simplify | 0.049 | 0.049 |
| pipbatch | 83.738 | 92.169 |

Стабильный выигрыш от смены runtime не подтверждён. Разброс между раундами
велик (union: 156–202 мс на .NET 10; пакетный PIP: 84–129 мс). Это сравнение
JIT/runtime одной сборки, не двух независимо скомпилированных библиотек.
Контрольные результаты совпали: 6075 / 3 / 249 / 787 соответственно.
Аллокации simplify и pipbatch: 0.080 и 2.407 МБ на повтор на обоих runtime.
Аллокации union менялись из-за состояния пулов (1.899–2.674 МБ), поэтому
этот короткий прогон не даёт надёжного сравнения аллокаций sweep.

Приоритетные направления, найденные в текущем коде:

1. **Повторные `PathsD` boolean-операции**: выполнено в следующем разделе.
  Один ограниченный движок на поток переиспользуется при совпадении precision;
  при смене precision создаётся новый. Кэш для нескольких precision не введён.
2. **Масштабирование входов `ClipperD`**: выполнено в разделе прямого ввода ниже.
  После проверки диапазона всего пакета вершины масштабируются сразу в арену,
  без промежуточных `Paths64` / `Path64`. Округление и Z-семантика сохранены.
3. **Пакетный PIP по многим полигонам**: текущий драйвер проверяет все точки
  против каждого пути. Пространственный индекс по bbox путей может сократить
  число пар вместо дальнейшего ускорения единичного предиката. API должен
  явно определять результат по каждому пути и обработку границ.
4. **Miter-offset**: остаётся кандидатом на свежий профиль AEL. Числа старых
  разделов ниже исторические; арены, POD-сортировка и инкрементальная площадь
  уже внедрены, повторять эти изменения не нужно.

Для каждого изменения: сравнение чередующимися A/B-раундами, отдельный учёт
аллокаций после прогрева пулов, `golden verify` (6409 хэшей), C++ fidelity,
Z golden и тесты на обеих целевых платформах. Перегрузки старого порядка
аргументов только перенаправляют вызовы и не добавляют геометрических аллокаций.

## Оптимизация 07.10.2026: повторные PathsD boolean-операции

Внедрены два изменения без смены алгоритма геометрии:

* `ClipperD.RentShared` / `ReturnShared`: один движок на поток, взятый движок
  исключается из кэша до завершения вызова. `try/finally` очищает входы даже
  после исключения; сбрасываются ошибки, флаги и оба Z-callback. Как у
  `Clipper64`, движок не сохраняется при `PooledObjectCount > 131072`.
* `InternalClipper.ScalePaths(PathsD, ...)` вычисляет bbox один раз вместо
  четырёх обходов. В версии 2.0.3 промежуточные целочисленные пути оставались; масштаб,
  округление и проверки диапазона не изменены.

Воспроизводимый A/B-драйвер:

```powershell
dotnet run -c Release --project benchmark/Clipper2.PortProfile -- booldcompare 10
dotnet --fx-version 11.0.0-preview.4.26230.115 benchmark/Clipper2.PortProfile/bin/Release/net10.0/Clipper2.PortProfile.dll booldcompare 10
```

Входы подготовлены до измерения, precision = 3. Сравниваются свежий `ClipperD`
и статический API; bbox-оптимизация действует на оба варианта. На каждый из
четырёх наборов: 700 мс прогрева, 6 чередующихся A/B-раундов (первый отброшен),
блоки не короче 200 мс и не меньше 10 проходов. Время ниже - лучший блок на
операцию, аллокации - байты текущего потока на операцию в последнем блоке.
Хэши всех координат, порядка путей и вложенности деревьев совпадают.

| .NET 10.0.12 | свежий, мкс | статический, мкс | ускорение | свежий, Б/оп | статический, Б/оп |
| --- | ---: | ---: | ---: | ---: | ---: |
| маленькие операции, PathsD | 1.661 | 1.268 | 1.31x | 5020 | 796 |
| маленькие операции, PolyTreeD | 1.780 | 1.474 | 1.21x | 5396 | 1172 |
| корпус, PathsD | 103.987 | 94.510 | 1.10x | 43190 | 15792 |
| корпус, PolyTreeD | 156.502 | 147.951 | 1.06x | 72092 | 44693 |

Исходный статический API до обеих оптимизаций выделял соответственно
5204 / 5580 / 43351 / 72252 Б/оп. Снижение к нему: 85% / 79% / 64% / 38%.
Добавление хранения precision увеличило размер свежего движка на 8 байт;
устранение повторных bbox-обходов убрало ещё 192 Б на маленькую операцию.

На .NET 11 Preview 4 тот же драйвер дал 1.47x / 1.27x / 0.94x / 1.05x;
статические аллокации те же. Для больших операций стабильный выигрыш по
времени не установлен: предыдущий .NET 10 прогон дерева корпуса дал 0.97x.
На загруженной машине эти короткие измерения не доказывают отсутствие
регрессии throughput. Подтверждённый результат - сокращение аллокаций;
наиболее полезный сценарий - повторные небольшие операции с одним precision.
Вызовы через собственный `new ClipperD` не используют кэш.

Проверки: 42 теста на каждом TFM (84/84), включая все precision от -8 до 8,
ошибки precision/диапазона, вложенную аренду, сброс открытых путей и настроек,
ограничение кэша, параллельные вызовы и порог снижения аллокаций. 6409/6409
golden-хэшей, 197/197 C++-случаев, Z golden `f8e159797c986f52` на обоих
runtime сохранены. Z-драйвер дополнительно сравнивает статические PathsD и
PolyTreeD с независимым движком по X/Y/Z и вложенности на 1500 fuzz-случаях.

## Оптимизация 07.10.2026: прямой ввод PathsD и короткий batch PIP

Оставлены два изменения с проверенной точностью и снижением аллокаций:

* `ClipperD.AddPaths` сначала проверяет диапазон всего пакета, затем масштабирует
  точки прямо в `VertexStore`. Общий построитель вершин специализируется на
  struct-конвертере; правила удаления повторов, открытых путей и локальных
  минимумов не дублируются. Сохранены бинарный масштаб движка, округление
  `AwayFromZero` и прежний конструктор координат, включая преобразование Z.
  Одиночный `AddPath` переиспользует контейнер на один путь и очищает его в
  `finally`, не удерживая пользовательский путь после вызова.
* `Clipper.PointInPolygon(PathD, points, results, precision)` для 1-15 точек
  масштабирует полигон один раз вместо одного раза на каждую точку. Порог
  prepared locator не менялся. Пустой batch по-прежнему не проверяет precision;
  проверка длины results и порядок ответов сохранены.

### PIP: воспроизводимый A/B

```powershell
dotnet run -c Release --project benchmark/Clipper2.PortProfile -- pipdcompare 10
dotnet --fx-version 11.0.0-preview.4.26230.115 benchmark/Clipper2.PortProfile/bin/Release/net10.0/Clipper2.PortProfile.dll pipdcompare 10
```

Контроль - цикл неизменённых одиночных PIP-вызовов, то есть прежняя работа
короткого batch. Каждый ответ предварительно сравнивается с контролем.
Полигон, точки и results подготовлены вне измерения, precision = 3.
Драйвер проверяет 1, 2 и 15 точек, 64 и 2000 вершин; 700 мс прогрева,
6 чередующихся раундов с отброшенным первым, блоки не короче 200 мс.
Время - лучший блок, память - байты текущего потока на batch.

| runtime, 15 точек | вершин | старый цикл, мкс | batch, мкс | ускорение | старый, Б | batch, Б |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| .NET 10.0.12 | 64 | 4.823 | 1.036 | 4.66x | 16200 | 1080 |
| .NET 10.0.12 | 2000 | 164.707 | 24.144 | 6.82x | 480840 | 32056 |
| .NET 11 Preview 4 | 64 | 4.590 | 1.076 | 4.27x | 16200 | 1080 |

Для двух точек аллокации уменьшились вдвое; ускорение на 2000 вершинах
1.89x / 1.87x. Для одной точки аллокации прежние, выигрыша нет: новый batch
в этих замерах дал 0.88-0.98x производительности одиночного вызова. Это накладные расходы
пакетного API относительно scalar-контроля, не замер старого batch против нового.
Числа выше относятся к этим конкретным входам, а не ко всем PIP-сценариям.

### PathsD boolean: независимая старая сборка

До изменения сохранена Release-сборка драйвера и библиотеки из `81845be`
(код библиотеки 2.0.3) в `artifacts/pre-direct-input`. Старый и новый
`booldcompare 10` запущены на .NET 10.0.12 дважды: сначала старый/новый,
затем новый/старый. Внутри каждого запуска сохраняется прежний шестираундовый
протокол свежий/статический. Четыре хэша координат и вложенности одинаковы
между сборками; ниже память статического API, одинаковая в обоих раундах:

| операция | 2.0.3, Б/оп | прямой ввод, Б/оп | снижение |
| --- | ---: | ---: | ---: |
| маленькие операции, PathsD | 796 | 428 | 46.2% |
| маленькие операции, PolyTreeD | 1172 | 804 | 31.4% |
| корпус, PathsD | 15792 | 14864 | 5.9% |
| корпус, PolyTreeD | 44693 | 43765 | 2.1% |

У больших boolean-операций устойчивый выигрыш времени не установлен;
подтверждённый результат прямого ввода - устранение временных входных путей
и сокращение памяти. Отдельный тест прогретого ввода 2000 вершин требует
более чем десятикратного снижения аллокаций относительно старого масштабирования.

Целочисленный путь проверен старой/новой сборками в трёх чередующихся раундах.
Результаты `union` / `offset27` прежние: 6075 / 3. Лучшие времена Miter-offset:
2.827 / 2.826 мс. Для union: 153.144 / 157.084 мс (новый минимум на 2.6% хуже),
при разбросе нового 157-452 мс; устойчивый эффект на загруженной машине не
установлен. Ускорение sweep не заявляется. Отложенная инициализация SEL,
изменения AEL и пространственный индекс по полигонам не внедрялись.

### Проверки

47 тестов на каждом TFM, 94/94 успешны. Новые регрессии проверяют precision
от -8 до 8, все ClipType/FillRule, порядок путей, открытые результаты и
вложенность дерева, PreserveCollinear/ReverseSolution, короткие/пустые PIP
batch и нетронутый хвост results. Эталон прямого ввода - неизменённое
`InternalClipper.ScalePaths` с подачей `Paths64` через integer-перегрузку
базового движка; результаты собираются одинаковым `ClipperD`. Это сохраняет
уже существующее отличие фильтрации коротких открытых путей от `Clipper64`.
Тест ошибки диапазона использует отдельный валидный путь перед невалидным:
проверяется отсутствие частичного добавления и восстановление после исключения.

6409/6409 golden-хэшей и Z golden `f8e159797c986f52` (1500 случаев) сохранены
на обоих runtime; C++ fidelity 197/197 на .NET 10. Новых диагностик в
изменённых исходниках нет. Эти изменения входят в версию пакета 2.0.4.

## 2. Новые измерения (этот раунд)

### 2.1 Чистый профиль порта на union (без эталонной библиотеки в процессе)

Бенчмарк грузит обе библиотеки в один процесс, а в трассе они обе печатаются
как `Clipper2Lib.*`, поэтому старые доли (`BuildIntersectList 12%` и т.д.)
были суммой двух реализаций. Профиль снят отдельным драйвером, который гоняет
только порт (`dotnet-trace collect` по умолчанию, 25 повторов union), доли
нормированы на время `Main` (поток финализатора исключён):

| фрагмент | доля union | комментарий |
|---|---:|---|
| `DoIntersections` (включительно) | **~83%** | вся фаза пересечений: построение списка, сортировка, обработка |
| сортировка `IntersectNode` (`IntroSort.Loop` + партиции + `Less`) | **~28%** | введённый в прошлом раунде introsort; он уже без делегатов, но двигает 32-байтные структуры с двумя ссылками |
| `BuildIntersectList` (эксклюзивно, с инлайном `AddNewIntersectNode`/`TopX`) | **~13%** | merge-обход SEL, `GetLineIntersectPt`, запись узлов |

| `IntersectEdges` (включительно) | ~6% | |
| `BuildPaths64` (включительно) | ~11% | из них `ClipperEngine.Area(OutPt)` — **7.2%**: `FixSelfIntersects` → `DoSplitOp` пересчитывает площадь всего контура O(n) на каждое расщепление |
| `AddLocalMinPoly` | ~3% | внутри `NewOutRec` каждый раз выделяет `new Path64()` |

### 2.2 Микробенчмарки (scratch-проект `predbench`, 4 млн вызовов, лучшее из 7)

Предикаты `a*b ? c*d` (то, что делает `CrossProductSign`/`IsCollinear`):

| вариант | коорд. ≤5e6 (данные тестов) | те же, почти коллинеарные | коорд. ≤5e11 |
|---|---:|---:|---:|
| `Int128` (сейчас в порте) | 12.3 нс | 9.5 нс | 10.5 нс |
| `Math.BigMul(long,long,out)` + сравнение (hi,lo) | 12.7 нс | 8.8 нс | 10.2 нс |
| **64-битный путь при всех \|v\| ≤ 2^31, иначе BigMul** | **9.5 нс** | 8.1 нс | 10.2 нс |
| + статический double-фильтр (Shewchuk-style) перед BigMul | 9.8 нс | 9.4 нс | 12.4 нс |
| равенство: `Int128` / BigMul / 64-бит+BigMul | 6.3 / 9.5 / **4.3** нс | 5.0 / 4.8 / 5.2 | 4.4 / 4.8 / 8.4 |

Расхождений с `Int128` — 0 на всех 16 млн четвёрок (включая почти
коллинеарные). Вывод: предикат уже близок к пределу; 64-битный ярус даёт
−20…−30% на «обычных» координатах, double-фильтр **не нужен** (входы целые,
точный 128-битный fallback и так дёшев) — отклонён по измерению.

Write barriers (то, чего нет у C++): те же операции на объектах-классах и на
struct-массиве с int-индексами:

| операция | классы (сейчас) | struct-арена | выигрыш |
|---|---:|---:|---:|
| проход «копировать AEL в SEL» (3 ссылочных поля + `currX`) | 6.3 нс/узел | 3.4 нс/узел | **1.9x** |
| `SwapPositionsInAEL` (6 ссылочных записей) | 11.1 нс | 3.3 нс | **3.4x** |
| introsort 100k `IntersectNode` (Point64 + 2 поля), тот же алгоритм | 200 нс/эл | 100 нс/эл | **2.0x** |

Это главное открытие раунда: отставание sweep'а — не арифметика, а стоимость
записи ссылок в кучу (card-marking barrier на каждой из десятков миллионов
перелинковок) и перемещения структур со ссылками при сортировке.

### 2.3 Статистика нагрузок

* point in polygon: из 49.8 млн пар «проба–путь» проба попадает в bbox пути в
  **2 220** случаях (0.004%); из 894 млн просканированных рёбер горизонталь
  пробы пересекают **4 444**. Строка бенчмарка почти целиком измеряет сканирование
  путей, к которым проба заведомо не относится.
* union: 249 путей образуют **4** компоненты по пересечению bbox, крупнейшая —
  246 путей. Параллелизм «по кластерам» на этих данных ничего не даст.

## 3. Диагноз

1. **Sweep проигрывает C++ на «сантехнике», а не на геометрии.** Ссылочные
   `Active`/`OutPt`/`Vertex` + `IntersectNode` со ссылками → write barriers и
   тяжёлые перемещения там, где C++ двигает указатели и POD.
2. **Сортировка узлов пересечений — крупнейший одиночный элемент (~28%)**, и
   её порядок при равных ключах нельзя менять (это стоило 36 случаев корпуса в
   прошлом раунде). Ускорять можно только представление, не алгоритм.
3. **`Area(OutPt)` в `FixSelfIntersects` — 7% чистого O(n²)**, унаследованного
   из C++; здесь порт может обогнать оригинал.
4. Предикаты, очередь сканлайнов, GC на больших строках — не узкие места.
5. Point-in-polygon одиночным вызовом упёрся в пол (~1.3 нс/вершина); реальный
   выигрыш только у batch/prepared API с отсечением по bbox и Y-индексом рёбер.

### Фаза 2 — арена движка: struct + индексы вместо ссылок (1.5–3 недели)

Это единственный путь к паритету и выше на большом sweep'е.

* **Что**: `Active`, `OutPt`, `Vertex`, `LocalMinima`, `OutRec` → `struct` в
  массивах (`Active[]`, `OutPt[]`, …) с `int` ссылками (`-1` = null);
  `IntersectNode` = `(Point64, int, int)`; списки AEL/SEL/jump — целые индексы.
  Алгоритм — построчно тот же (порт уже line-by-line), меняется только адресация:
  `e.nextInAEL` → `actives[e].nextInAEL`. Пулы становятся тривиальными
  (`count = 0`), `ReuseableDataContainer64` — массив вершин + массив минимумов.
* **Почему**: измерено 1.9x/3.4x/2.0x на именно тех операциях, которые
  составляют ~70% union (BuildIntersectList, ProcessIntersectList, сортировка,
  IntersectEdges, AddOutPt). Дополнительно: массивы структур лежат плотно,
  `Point64` не копируется при обращении через `ref`.
* **Как, чтобы не сломать точность**: механический перевод по одной структуре:
  сначала `Active` (AEL/SEL — самое горячее, все `Swap*/Insert*/Extract*`),
  затем `IntersectNode`, затем `OutPt`, затем `Vertex`/`LocalMinima`. После
  каждого шага — корпус 197 + фаззер против старого движка (оракул) + тесты.
  Старый движок остаётся в дереве до конца фазы (как `#if` или отдельный тип
  в тест-проекте) — он и есть эталон.
* **Ожидание**: −25…−35% union (сверх фазы 1) → ≈ 1.0–1.15x C++ на самой
  тяжёлой строке; те же проценты на boolean ops и offsets; аллокации на «мелких»
  строках падают до одного буфера на тип.
* **Риск**: только ошибки трансляции (индекс вместо null, стейл-индекс после
  переиспользования). Арифметика не меняется → результат обязан быть бит-в-бит.
  Для `Active` C++ тоже выделяет объекты по одному — паритет представления не
  требуется, только эквивалентность.
* **Что не делать**: не менять порядок обработки узлов, не трогать introsort,
  не вводить `Math.FusedMultiplyAdd` в предикаты/пересечения (это уведёт
  результат к `-march=native`-сборке, а не к `-O2`).

### Фаза 3 — новые API там, где одиночный вызов упёрся в пол (1 неделя)

* **`PointInPolygon` для пакетов** (§5.3): `PolygonLocator`/`PreparedPath64`
  с bbox и Y-индексом рёбер; `Clipper.PointsInPolygon(path, ReadOnlySpan<Point64>,
  Span<PointInPolygonResult>)`. На данных бенчмарка отсекается 99.996% пар;

* **Параллельный union по компонентам** (§5.4): union-find по bbox, каждый

  масштабирование. Только для `Paths64`-выхода, с оговоркой о порядке путей;

## 5. Математические приёмы

### 5.1 Точная инкрементальная площадь (Int128-шнуровка)

Сумма шнуровки `Σ (y_prev + y) (x_prev − x)` для 64-битных координат —
целое число, помещающееся в 128 бит. В целых числах сложение ассоциативно,
поэтому площадь контура можно **поддерживать инкрементально**: при расщеплении
в `DoSplitOp` из контура уходят две вершины и приходит `ip`, т.е. из суммы
вычитаются 3–4 слагаемых и добавляются 2–3. Стоимость O(1) вместо O(n), и
значение в точности равно пересчёту с нуля (чего в double гарантировать
нельзя). Знак и `|area| < 2` проверяются по точному значению; `AreaTriangle`
тоже точен в Int128. Единственное отличие от C++ — там площадь в double с
ошибкой округления; расхождение возможно только когда double-значение
находится в пределах ошибки от порога решения. Это тот же класс отличий, что
между `-O2` и `-march=native` сборками C++, и его нужно оформить как
задокументированное свойство (корпус + фаззер должны показать 0 отличий).

### 5.2 Ярусный точный ориентационный предикат

`sign(a·b − c·d)` при всех |a|,|b|,|c|,|d| ≤ 2^31 вычисляется в `long` без
переполнения (|a·b| ≤ 2^62). Проверка одним выражением:
`m = (a ^ (a>>63)) | (b ^ (b>>63)) | (c ^ (c>>63)) | (d ^ (d>>63)); (ulong)m < 2^31`
(дополнение до единицы даёт |v| или |v|−1 — для границы это безопасно).
Иначе — `Math.BigMul(long, long, out long)` (одна инструкция `imul` на x64)
и сравнение пары (hi signed, lo unsigned). Прошлая попытка «64-битного
быстрого пути» была отклонена из-за ошибки в guard'е (OR знаковых значений),
а не из-за идеи; тест на координаты 9e9 остаётся. Статический double-фильтр
измерен и отклонён (§2.2).

### 5.3 Пакетная локализация точки: bbox + Y-индекс рёбер

Для полигона строится один раз: bbox, массив рёбер с `[ymin, ymax]`,
отсортированный по `ymin` (или корзины по Y, если проб много). Запрос: если
точка вне bbox → `IsOutside` без сканирования; иначе перебираются только рёбра,
у которых `ymin ≤ pt.Y ≤ ymax` (на данных бенчмарка это 4 444 ребра из 894 млн).
Эквивалентность текущему алгоритму: результат `IsOn` возвращается, если **хоть
одно** ребро удовлетворяет условию касания/коллинеарности — порядок обхода не
важен; чётность пересечений слева — сумма по рёбрам, тоже порядконезависима;
вершины, лежащие на горизонтали пробы, обрабатываются тем же правилом
(полуоткрытый интервал по Y), которое нужно перенести дословно и покрыть
дифференциальным тестом против `PointInPolygon` на случайных полигонах.

### 5.4 Разложение на независимые компоненты для параллельного клиппинга

Пути, чьи bbox не пересекаются транзитивно, никогда не взаимодействуют в
sweep'е: пересечений между ними нет, а вклад замкнутого полигона в winding
count рёбер правее него равен нулю (он пересекает любую горизонталь чётное
число раз с чередующимися направлениями). Поэтому `Union` кластера равен его
части в общем `Union`, и кластеры можно считать параллельно. Меняется только
порядок путей в выходе — его нормализуем (сортировка по стабильному ключу,
например (minY, minX) первой вершины) и документируем.

### 5.5 Рассмотрено и отклонено по измерениям

* **Предвычисленное расписание сканлайнов** (отсортированные уникальные Y
  вершин вместо max-heap): heap = 0.1% профиля; на корпусе всего 257 Y. Нет.
* **Double-фильтр Шевчука перед точным предикатом**: на целых входах медленнее
  точного BigMul-пути. Нет.
* **SIMD-скан Y в одиночном `PointInPolygon`**: пути в среднем по 18 вершин,
  скан уже ~1.3 нс/вершина; выигрыш утонет в накладных на вызов. Только как
  часть 5.3 для длинных полигонов.
* **Замена алгоритма сортировки узлов** (radix/стабильная): меняет порядок
  равных ключей → теряет бит-точность (36 случаев в прошлом раунде). Нет.
* **`atan2`-free подсчёт шагов дуг в offset**: доля `Math.Atan2` в offset-строках
  незначительна, всё время — в финальном union. Нет.
* **`float`/`Half`**: уже отклонены в прошлом раунде с цифрами (README).

## 6. Порядок работ и критерии приёмки

1. Фаза 0 → фаза 1 (пункты 1.1, 1.2, 1.3, 1.4 дают ~25% union и самые дешёвые;
   1.7–1.10 — по одному коммиту на строку бенчмарка).
2. После каждого пункта: `dotnet test`, корпус 197 бит-в-бит, фаззер, замер
   `--only=` строки против `Results/baseline.json`; принимаем только при
   0 отличий в корпусе и выигрыше ≥ шума (≥15%) либо подтверждённом на 3 сессиях.
3. Фаза 2 — отдельная ветка, слияние только после полного зелёного контура и
   обновления `Results/BASELINE.md` (`--write-baseline` + `record-baseline.ps1`).
4. Цели раунда: union ≥ 1.0x C++, PIP-пакетный API ≥ 50x текущей строки,
   boolean ops ≥ 1.6x C++, триангуляция ≥ 1.4x, rect clip ≥ 1.4x, аллокации
   на всех строках ≤ эталонного C# порта.

## 7. Артефакты этого раунда

* Микробенчмарки: scratch-проект `predbench` (предикаты, write barriers,
  сортировка узлов) — перенести в `benchmark/Clipper2.MicroBench` в фазе 0.
* Драйвер «только порт»: scratch `unionprof` (режимы `union`, `pip`,
  `pipstats`, `clusters`, `stats`) — основа для `Clipper2.PortProfile`.
* Трасса `union-port.nettrace` (25 повторов union, порт без эталона).
